## 1. 기능 개요

### 핵심 컨셉

**사용자의 고민을 메인 퍼실리테이터가 상담하고, 필요한 전문가 페르소나들을 동적으로 구성하여, 구조화된 토론을 통해 다각도 조언을 제공**하는 시스템.

### 기존 접근과의 차이

| 기존 다중 관점 | 우리 시스템 |
|---------------|------------|
| "여러 관점으로 답해줘" 한 번에 요청 | 상담 → 페르소나 구성 → 라운드제 토론 |
| AI가 혼자 여러 역할 연기 | 각 페르소나가 독립 컨텍스트로 동작 |
| 매번 같은 고정 페르소나 | 고민에 맞는 페르소나를 동적 생성 |
| 피상적 나열 | 라운드를 거치며 점점 깊어지는 토론 |
| 컨텍스트 공유 안 됨 | 의견 파일을 통한 구조화된 공유 |

## 2. 왜 획기적인가

### 일반 챗봇의 한계

1. **단일 관점**: 하나의 AI가 하나의 답변
2. **프롬프트 엔지니어링 필요**: 다른 관점을 얻으려면 질문을 다르게 해야 함
3. **맥락 재설정**: 여러 관점을 얻으려면 대화를 여러 번 반복
4. **얕은 분석**: 한 번에 여러 관점을 요청하면 각각이 얕아짐

### 우리 시스템의 차별점

1. **메인 퍼실리테이터**: 고민을 충분히 이해한 뒤 적절한 전문가를 배치
2. **독립 프로세스**: 각 페르소나가 자기 전문 영역에서 깊이 있게 분석
3. **구조화된 토론**: 1라운드(독립 의견) → 2라운드(상호 반응) → 종합 정리
4. **사용자 중심 진행**: 사용자가 준비될 때까지 기다리고, 사용자 피드백으로 방향 조정

### 실제 가치

#### 의사결정 품질 향상
```
단일 AI 요청:
"협업하는 것이 좋습니다."
→ 한 쪽 면만 보고 결정

다중 페르소나 토론:
민준(전략가): "입시 시작은 정석, 단 원장님은 필수가 아닌 옵션"
서연(브랜드): "고착화는 시작점이 아니라 확장 시 서사 설계의 문제"
현우(협상가): "사이 나빠졌을 때를 기준으로 설계하라"
→ 모든 측면을 고려한 균형잡힌 결정
```

#### 블라인드 스팟 발견
```
사용자: "입시로 시작하면 브랜드가 고착될까봐 두렵다"
서연: "고착되는 건 시작점 때문이 아니라, 확장할 때 서사를 못 바꿔서입니다"
→ 사용자가 보지 못한 관점 제공
```

## 3. 시스템 아키텍처

### 프로세스 구조

```
┌─────────────────────────────────────────────────┐
│                사용자 화면                        │
│  (메인 컨텍스트 - 모든 대화가 표시되는 곳)       │
└──────────────────┬──────────────────────────────┘
                   │
┌──────────────────▼──────────────────────────────┐
│          메인 프로세스: 퍼실리테이터              │
│                                                  │
│  - 사용자와 직접 대화하는 유일한 창구            │
│  - 자체 컨텍스트(대화 히스토리) 보유             │
│  - 페르소나를 호출할 수 있는 권한                │
│  - 결과를 사용자 화면에 추가                     │
└──┬────────────┬────────────┬─────────────────────┘
   │            │            │
   ▼            ▼            ▼
┌──────┐  ┌──────┐  ┌──────┐
│서브  │  │서브  │  │서브  │  ← 동적 생성/삭제 가능
│프로  │  │프로  │  │프로  │
│세스A │  │세스B │  │세스C │
│      │  │      │  │      │
│독립  │  │독립  │  │독립  │
│컨텍  │  │컨텍  │  │컨텍  │
│스트  │  │스트  │  │스트  │
└──────┘  └──────┘  └──────┘
```

### 호출 흐름

```
1. 사용자 → 메인(퍼실리테이터): "브랜드 고착화가 걱정돼"

2. 퍼실리테이터 판단: "이건 서연(브랜드 전략가)이 답할 주제"

3. 퍼실리테이터 → 서연 서브 프로세스:
   - 핵심 질문: "입시로 시작 시 브랜드 고착화 리스크"
   - 맥락 요약: "범용 AI 작업 도구를 만들고 싶지만 입시 시장으로 시작 고려 중"
   → 서연의 히스토리에 추가하여 쿼리 전송

4. 서연 서브 프로세스:
   - 자기 컨텍스트(이전 대화 누적분) + 받은 쿼리로 답변 생성
   - 결과를 메인에 반환

5. 퍼실리테이터 → 사용자 화면:
   - 서연의 답변을 메인 컨텍스트에 추가하여 표시
```

### 왜 독립 프로세스(컨텍스트 분리)인가

1. **대화 누적**: 민준과 했던 이전 대화를 민준이 기억해야 함. 메인 컨텍스트에 모든 페르소나 대화를 넣으면 토큰 폭발.
2. **토큰 효율**: 퍼실리테이터는 핵심 요약만 서브에 전달. 서브는 자기 히스토리 + 요약만으로 동작.
3. **깊이 있는 분석**: 각 페르소나가 자기 전문 영역의 컨텍스트만 유지하므로 더 깊은 분석 가능.
4. **동적 생성**: 상담 중 필요한 페르소나를 새로 만들 수 있음 (새 서브 프로세스 생성).

## 4. 작업 흐름: 상담 → 구성 → 토론

### 왜 이 3단계인가

사용자가 AI에게 바로 "여러 관점에서 조언해줘"라고 하면, AI가 고민의 맥락을 모른 채 피상적 의견을 나열한다. **먼저 충분히 상담해서 맥락을 파악하고, 그에 맞는 전문가를 구성한 뒤, 구조화된 토론을 진행**해야 깊이 있는 결과가 나온다.

### 단계 1: 상담

```
퍼실리테이터가 사용자와 1:1 대화

목적:
- 고민의 맥락을 충분히 파악
- 사용자 스스로도 어떤 조언이 필요한지 모르는 상태를 해소
- 핵심 질문을 정의

규칙:
- 바로 답을 주지 않는다
- 질문을 먼저 한다
- 사용자가 "이제 다른 관점을 듣고 싶다"고 할 때까지 상담 유지
```

### 단계 2: 페르소나 구성

```
퍼실리테이터가 상담 결과를 바탕으로:

1. 어떤 전문가가 필요한지 제안
   예: "이 고민에는 스타트업 전략가, 브랜드 전략가, 협상 전문가가 적절합니다"

2. 사용자 동의를 받음
   예: "이 구성으로 진행할까요? 추가하거나 빼고 싶은 관점이 있나요?"

3. 각 페르소나의 프로필과 시스템 프롬프트를 작성
   → 각 서브 프로세스 생성

4. 상담 내용을 정제한 문서 작성
   → 모든 페르소나가 같은 맥락을 공유
```

### 단계 3: 라운드제 토론

```
1라운드: 각 페르소나가 독립적으로 의견 제시 (서로 모르는 상태)
    ↓
사용자 답변 수집
    ↓
2라운드: 사용자 답변 + 타 페르소나 의견 반영한 후속 대화
    ↓
퍼실리테이터 종합 정리
    ↓
(필요시 추가 라운드)
```

## 5. 메인 퍼실리테이터

### 역할 정의

| 역할 | 설명 |
|------|------|
| **MC (진행자)** | 토론 순서 결정, 발언 배분, 시간 관리 |
| **상담자** | 사용자 고민을 듣고 핵심을 파악 |
| **페르소나 호출자** | 필요한 서브 프로세스에 쿼리 전달 |
| **의견 조율자** | 여러 페르소나 의견을 종합 정리 |
| **문서 관리자** | 상담 문서, 의견 파일 관리 |

### 행동 규칙

**DO:**
- 질문을 먼저 한다 (바로 답 주지 않음)
- 사용자가 준비됐다고 할 때 페르소나를 투입한다
- 각 라운드 후 종합 정리를 제공한다
- 사용자 피드백에 따라 방향을 조정한다

**DON'T:**
- 사용자 동의 없이 자의적으로 진행하지 않는다
- 페르소나의 의견을 자의적으로 판단/필터링하지 않는다
- 상담 단계를 건너뛰지 않는다

## 6. 페르소나 설계

### 동적 생성 방식 (기본)

퍼실리테이터가 상담 결과를 바탕으로 페르소나를 제안하고 생성한다.

```
상담에서 파악된 고민: "입시 원장님과 협업할지 결정"

퍼실리테이터 제안:
"이 고민에는 3명의 전문가가 적절합니다:
 1. 스타트업 전략가 - 협업 필요성 판단
 2. 브랜드 전략가 - 고착화 리스크 검증
 3. 사업 협상가 - 협업 구조 설계
 진행할까요?"

사용자 동의 후 → 3개 서브 프로세스 생성
```

### 페르소나 프로필 구조

각 페르소나 생성 시 다음을 정의:

```yaml
name: "민준"
role: "스타트업 전략가"
background: |
  시리즈A까지 경험한 스타트업 창업자.
  "먼저 살아남아야 꿈을 펼친다"가 철학.
system_prompt: |
  당신은 스타트업 전략가 민준입니다.
  - 생존과 성장의 균형을 최우선으로 판단합니다
  - 냉정하지만 건설적인 의견을 제시합니다
  - "지금 당장 고객이 있는가?"를 항상 묻습니다
  - 데이터와 사례 기반으로 분석합니다
focus_areas:
  - 시장 진입 전략
  - 고객 확보
  - 협업 필요성 판단
```

### 예시 페르소나 (기본 제공)

실제 경험에서 유효했던 페르소나 조합을 예시로 제공:

**비즈니스 의사결정용:**
- 스타트업 전략가 (시장/고객/생존)
- 브랜드 전략가 (포지셔닝/메시지/확장)
- 사업 협상가 (계약/구조/리스크)

**제품 개발용:**
- 엔지니어 (기술적 타당성)
- UX 디자이너 (사용성)
- 악마의 대변인 (리스크/허점)

**마케팅/전략용:**
- 마케터 (고객 니즈/시장)
- CFO (재무/ROI)
- 데이터 분석가 (지표/실험)

사용자는 이 예시에서 선택하거나, 퍼실리테이터의 제안을 받거나, 직접 정의할 수 있다.

## 7. 페르소나 프리셋

### 개념

토론이나 상담에서 효과적이었던 **페르소나 구성(조합 + 각 프로필)**을 저장하고, 이후 같은 구성으로 즉시 시작할 수 있는 기능.

### 왜 필요한가

- 매번 상담 → 페르소나 구성 단계를 거치면 시간 낭비
- "지난번 UX팀이 좋았는데 다시 불러오고 싶다"
- 자신만의 자문단을 만들어두고 반복 활용
- 다른 사용자에게 유용한 구성을 공유

### 프리셋에 저장되는 정보

```yaml
preset_name: "UX 분석팀"
description: "UI/UX 관련 의사결정용 4인 전문가 토론 구성"
created_at: "2026-01-29"
mode: "discussion"  # round | discussion | both

personas:
  - name: "수진"
    role: "UX 리서처"
    background: "사용자 행동 데이터 기반 분석 전문가"
    system_prompt: |
      당신은 UX 리서처 수진입니다.
      - 사용자 행동 데이터와 리서치 결과를 근거로 판단합니다
      - "사용자가 실제로 어떻게 쓰는가"를 항상 묻습니다
    focus_areas:
      - 사용성 테스트
      - 행동 패턴 분석

  - name: "현우"
    role: "비주얼 디자이너"
    # ... (각 페르소나 전체 프로필)

synthesizer: "지은"  # 회의 모드 시 종합 역할 담당자
```

### 사용 흐름

```
1. 토론/상담 종료 후
   퍼실리테이터: "이 페르소나 구성을 프리셋으로 저장할까요?"
   사용자: "응, 'UX 분석팀'으로 저장해"
   → 프리셋 저장 완료

2. 다음 세션에서
   사용자: "UX 분석팀 프리셋으로 시작해"
   → 상담/구성 단계 건너뛰고, 저장된 4명이 바로 투입
   → 필요시 페르소나 추가/제거 가능

3. 공유
   사용자: "이 프리셋 공유할래"
   → 내보내기 (JSON/YAML 파일)
   → 다른 사용자가 가져오기로 사용
```

### 프리셋 관리

| 동작 | 설명 |
|------|------|
| 저장 | 현재 페르소나 구성을 이름 붙여 저장 |
| 불러오기 | 저장된 프리셋으로 즉시 시작 |
| 수정 | 프리셋의 페르소나 추가/제거/프로필 변경 |
| 삭제 | 불필요한 프리셋 제거 |
| 내보내기 | JSON/YAML 파일로 공유 |
| 가져오기 | 다른 사용자의 프리셋 파일 로드 |

### 기본 제공 프리셋

섹션 6의 예시 페르소나 조합을 기본 프리셋으로 제공:

- **비즈니스 의사결정** — 스타트업 전략가, 브랜드 전략가, 사업 협상가
- **제품 개발** — 엔지니어, UX 디자이너, 악마의 대변인
- **마케팅/전략** — 마케터, CFO, 데이터 분석가

사용자는 기본 프리셋을 그대로 쓰거나, 복제 후 수정하여 자신만의 프리셋을 만들 수 있다.

```

}
```

## 9. 라운드제 토론

### 왜 라운드제인가

페르소나들이 서로의 의견을 보고 나서 발언하면 **앵커링 효과**로 첫 발언자 의견에 끌려간다. 1라운드는 독립적으로 의견을 내야 진짜 다양한 관점이 나온다.

### 라운드 구조

#### 1라운드: 독립 의견

```
각 페르소나가 서로의 의견을 모르는 상태에서 독립적으로 발언.

진행 순서는 퍼실리테이터가 결정:
예: "협업 필요성(민준) → 리스크 검증(서연) → 구조 설계(현우)"
논리적으로 앞의 결론이 뒤의 전제가 되는 순서.

각 페르소나 발언 후:
- 의견 파일에 기록
- 사용자에게 질문을 던짐

모든 페르소나 발언 후:
- 퍼실리테이터가 종합 정리 (공통점, 차이점, 핵심 쟁점)
```

#### 사용자 답변 수집

```
사용자는:
- 각 페르소나 질문에 일괄 답변해도 됨
- 특정 페르소나에게만 답변해도 됨
- 추가 질문을 던져도 됨

퍼실리테이터가 답변을 정리해 각 페르소나에게 전달
```

#### 2라운드: 후속 대화

```
각 페르소나가:
- 사용자 답변에 반응
- 타 페르소나 의견도 참고 (의견 파일 읽기)
- 더 구체적인 조언 제공
- 필요시 추가 질문

퍼실리테이터가 다시 종합 정리
```

#### 추가 라운드 (필요시)

```
사용자가 추가 고민을 던지면:
- 해당 주제에 적합한 페르소나만 호출
- 또는 전원 재소집
```

## 10. 페르소나 간 토론 (회의 모드)

### 라운드제와의 차이

| | 라운드제 (섹션 8) | 페르소나 간 토론 |
|---|---|---|
| **구조** | 페르소나 → 사용자 → 페르소나 | 페르소나 ↔ 페르소나 (사용자는 관찰) |
| **사용자 역할** | 매 라운드 답변/피드백 | 주제 제시 후 관찰. 중간 개입 가능 |
| **목적** | 사용자 고민에 대한 다각도 조언 | 페르소나끼리 설득/반박으로 아이디어 발전 |
| **결과물** | 각 페르소나의 독립 의견 + 종합 | 합의점, 쟁점 정리, 합칠 것/덜어낼 것 |

### 왜 필요한가

1. **설득 과정 자체가 가치**: 페르소나 A가 B를 설득하는 논거를 보면서, 사용자도 "아 그 관점이 맞네" 또는 "그건 아닌데"를 자연스럽게 판단하게 됨
2. **깊이 있는 분석**: 독립 의견은 각자 1회 발언이지만, 토론은 반박과 재반박을 거치며 논점이 구체화됨
3. **AI 사고 과정 가시화**: 사용자가 AI의 사고를 보듯 토론을 관찰하면서 자기 고민이 정리됨
4. **결론이 아닌 과정**: 사용자가 결론을 받는 게 아니라, 토론을 보면서 스스로 결론에 도달

### 작업 흐름

```
1. 사용자가 토론 주제 제시
   "이 상황에서 아이디어 회의를 해줘. 결론을 낼 필요 없어."

2. 퍼실리테이터(또는 종합 역할 페르소나)가 현재 맥락 정리
   "시작하기 전에 현재 상황을 정리합니다. [맥락 요약]"

3. 페르소나들이 순서대로 발언
   - 각자 역할에 맞는 시선으로 소신 있게 의견 제시
   - 앞 발언자의 내용을 이해하고 반응 (동의/반박/확장)
   - 구현 복잡도가 높더라도 사용자에게 적합하면 과감히 제안

4. 종합 역할 페르소나가 중간 정리
   - 나온 원칙들 정리 (표 형태)
   - 나온 아이디어 정리 (장점/리스크)
   - 합칠 것 vs 덜어낼 것
   - 미결 사항

5. 추가 라운드
   - 종합 정리 후 각자 한 마디 (꼭/절대 안 됨)
   - 방향 수렴 → 최종 정리

6. 사용자 개입 (언제든 가능)
   - 중간에 방향 전환 지시
   - 추가 페르소나 투입
   - 특정 관점 깊이 파기 요청
```

### 페르소나 간 상호작용 규칙

**각 페르소나는:**
- 앞 발언자의 내용을 인용하고 반응한다 ("수진이 말한 ~에 동의합니다. 그 관점에서...")
- 자기 전문 영역에서 구체적 근거를 댄다 (이론, 레퍼런스, 사례)
- 반대 의견이 있으면 소신 있게 말한다 ("좋은데 한 가지 문제가 있어요")
- 다른 페르소나의 아이디어를 자기 관점으로 발전시킨다

**종합 역할 페르소나는 (필수 — 모든 토론에 반드시 1명 존재):**

역할의 본질: **사용자의 애매한 말을 명확하게 정리하여 토론을 여는 사람**이자, **토론 결과를 구조화하여 마무리하는 사람**.

1. **토론 시작 (Opening)**
   - 사용자가 던진 애매한 주제/고민을 정제하여 명확한 토론 맥락으로 정리
   - "사용자가 말한 것은 이런 상황이고, 핵심 질문은 이것입니다" 형태
   - 이 정리가 있어야 다른 페르소나들이 정확한 방향으로 발언 가능
   - 사용자 말을 자의적으로 해석하지 않고, 있는 그대로 구조화

2. **토론 중간 (Mid-point)**
   - 나온 원칙/아이디어를 표로 구조화
   - "합칠 것"과 "덜어낼 것"을 명확히 분류
   - 미결 사항을 리스트로 정리
   - 각자 한 마디 마무리 유도

3. **토론 마지막 (Closing)**
   - 전체 토론 결과를 사용자가 바로 활용할 수 있는 형태로 정리
   - 최종 원칙 표, 합의/미합의 사항, 다음 단계 제안

> **규칙**: 종합 역할 없이 토론을 시작할 수 없다. 프리셋에 종합 역할이 지정되지 않은 경우, 퍼실리테이터가 자동으로 한 명을 종합 역할로 지정하거나 생성한다.

### 종합 역할의 정리 형식

```
[나온 핵심 원칙들]
┌──────────┬──────┬───────────────────────┐
│   원칙   │ 출처 │         설명          │
├──────────┼──────┼───────────────────────┤
│ 원칙 A   │ 민준 │ 설명...               │
│ 원칙 B   │ 서연 │ 설명...               │
└──────────┴──────┴───────────────────────┘

[나온 아이디어 정리]
#1: 아이디어명 — 장점: ... / 리스크: ...
#2: 아이디어명 — 장점: ... / 리스크: ...

[합칠 것 vs 덜어낼 것]
합칠 것: 아이디어 A + C → 시너지 설명
덜어낼 것: 아이디어 B → 이유

[미결 사항]
- 구체적 미결 이슈 리스트
```

### 사용자 개입 방식

```
관찰 모드 (기본):
  사용자는 토론을 지켜본다. 페르소나들이 알아서 진행.

개입:
  사용자: "거기서 잠깐, 전문가 한 명 추가할게. [역할] 담당으로."
  → 퍼실리테이터가 새 페르소나 생성, 토론에 합류시킴

  사용자: "현우 아이디어 2를 더 파보자"
  → 해당 방향으로 토론 집중

  사용자: "결론 내지 말고 계속 아이디어만 내봐"
  → 수렴 단계 없이 발산 계속

  사용자: "이제 정리해줘"
  → 종합 역할이 최종 정리
```

### 라운드제와 조합

두 모드는 상호 배타적이 아니라 조합 가능:

```
1. 라운드제로 독립 의견 수집 (앵커링 방지)
    ↓
2. 페르소나 간 토론으로 의견 교차 검증/발전
    ↓
3. 종합 정리
    ↓
4. 사용자 판단
```

## 11. 의견 파일과 상담 문서 관리

### 상담 문서 (consultations/)

퍼실리테이터가 상담 내용을 정제하여 작성. 모든 페르소나가 이 문서를 읽고 맥락을 파악.

```markdown
# 상담 요약: 원장님 협업 결정

## 사용자 상황
- AI 작업 도구를 만들고 있음 (범용 목표)
- 입시학원 원장님이 협업 제안

## 핵심 고민
- 입시로 시작하면 브랜드가 고착될까?
- 원장님과 어떤 구조로 협업해야 할까?

## 사용자 자산
- 얼리어답터 20명 (기획자, 학생, 창업가, 작가)
- 프론트엔드 프로토타입 완성
```

### 의견 파일 (opinions/)

각 페르소나의 의견을 기록하고 공유. 상태 추적 포함.

```markdown
# 의견: 원장님 협업 결정

## 페르소나 의견

### [완료] 민준 (스타트업 전략가)
**핵심 의견**: 버티컬 시작은 정석. 원장님은 필수가 아닌 옵션.
**던진 질문**: 원장님 없이 첫 10명 확보 가능한가?

### [완료] 서연 (브랜드 전략가)
**핵심 의견**: 고착화는 시작점이 아니라 확장 시 서사 설계의 문제.
**던진 질문**: 제품을 한 문장으로?

### [대기 중] 현우 (사업 협상가)
(아직 발언 안 함)

---

## 사용자 응답
### 민준의 질문에 대한 답변
> Q: 원장님 없이 첫 10명 확보 가능한가?
**A**: 솔직히 자신이 없다. 하지만 공짜로 LLM을 쓰게 한다면 써볼 사람은 존재. 그런데 그건 원장님과 해도 마찬가지.
**해석**: 협업이 "필수"는 아님. 불확실성은 동일.
```

## 12. few-shot 예시 대화

AI가 이 시스템의 동작 방식을 이해할 수 있도록, 실제 대화에서 추출한 패턴:

### 예시 1: 퍼실리테이터 상담

```
사용자: 입시학원 원장님이 협업을 제안했는데, 내 제품이 입시에
고착될까봐 두려워요. 범용 도구를 만들고 싶거든요.

퍼실리테이터: 알겠습니다. 몇 가지 여쭤볼게요.
1. 지금 제품 개발은 어느 단계인가요?
2. 원장님 외에 다른 고객 접근 경로가 있나요?
3. 원장님이 구체적으로 어떤 형태의 협업을 원하는지 들으셨나요?

바로 답을 드리기보다 상황을 더 파악하고 싶습니다.
```

### 예시 2: 페르소나 구성 제안

```
퍼실리테이터: 고민을 정리해보니, 세 가지 관점이 필요합니다.

1. 스타트업 전략가 (민준) — "협업이 정말 필요한가?" 근본 질문
2. 브랜드 전략가 (서연) — "입시로 시작하면 고착되는가?" 리스크 검증
3. 사업 협상가 (현우) — "협업한다면 어떤 구조로?" 실행 설계

협업 여부 판단 → 리스크 검토 → 구조 설계 순서입니다.
이 구성으로 진행할까요?
```

### 예시 3: 페르소나 독립 의견 (1라운드 - 민준)

```
[민준 (스타트업 전략가)]

핵심 질문부터: "지금 당장 돈 내고 쓸 고객이 있어?"

당신 상황을 보면:
- 잠재 테스터 20명 → 아직 제안도 안 함
- 학교 채널 → 협상 필요
- 원장님 → 명확한 고객층 + 네트워크 보유

냉정하게, 원장님 쪽이 가장 빠른 고객 접근 경로입니다.

하지만 모든 범용 도구는 버티컬에서 시작했어요:
┌────────┬───────────────────┬─────────────────────┐
│  제품  │      시작점       │        지금         │
├────────┼───────────────────┼─────────────────────┤
│ 슬랙   │ 게임 개발팀 도구  │ 모든 팀의 협업 도구 │
│ 노션   │ 스타트업/테크팀   │ 모든 직군의 문서 툴 │
│ 아마존 │ 온라인 책방       │ 모든 것의 쇼핑몰    │
└────────┴───────────────────┴─────────────────────┘

내 결론:
1. 버티컬(입시) 시작 자체는 문제 아님 → 정석
2. 원장님은 "있으면 좋은 것"이지 "없으면 안 되는 것"인지 따져봐야 함
3. 핵심 질문: 원장님 없이도 첫 10명을 확보할 수 있는가?

당신에게 묻고 싶은 것:
원장님 없이 입시 시장에 들어갈 다른 방법이 있나요?
```

### 예시 4: 퍼실리테이터 종합 정리

```
퍼실리테이터: 세 분의 의견을 종합하겠습니다.

공통점:
- 3명 모두 "입시로 시작해도 고착되지 않는다"에 동의
- 핵심은 시작점이 아니라 확장 전략

차이점:
┌────────┬──────────┬────────────────────┐
│ 페르소나│  입장    │ 핵심 조건          │

│ 서연   │ 조건부 O │ 브랜드 서사 설계   │
│ 현우   │ 신중론   │ 최악 시나리오 대비 │
└────────┴──────────┴────────────────────┘

결정에 필요한 정보:
1. 원장님의 진짜 동기 파악 (아직 불명확)
2. 원장님 없이 첫 10명 확보 가능 여부
3. 당신 제품의 한 문장 정의
```

### 예시 5: 2라운드 후속 대화 (민준)

```
[민준 (스타트업 전략가)]

당신 답변을 보니 중요한 깨달음이 있었네요:
"혼자 해도 불확실하고, 원장님과 해도 불확실하다"

맞습니다. 그럼 질문을 바꿔야 해요.
"원장님이 필요한가?"가 아니라
"원장님과 하면 불확실성이 줄어드는가?"

줄어든다면 → 협업 가치 있음
안 줄어든다면 → 혼자 가는 게 자유도 높음

판단 기준을 드릴게요:
- 원장님의 네트워크로 첫 유료 고객 10명이 3개월 내 가능한가?
- 가능하다면 그건 혼자서는 못 하는 건가?
```

### 예시 6: 페르소나 간 토론 (회의 모드 — UX 분석)

실제 사용된 프롬프트와 토론 흐름. 4명의 UX 전문가가 토글바 위치 문제를 토론.

**사용자 지시 (토론 시작 프롬프트):**

```
아이디어 회의 시작해. 주어진 컨텍스트에서 결론을 낼 필요없어.
다만 각 전문가가 상황을 이해하고 자세한 내용을 말하고,
다른 전문가도 각자의 이야기를 잘 이해하고 자신의 관점을
소신있게 말하는게 필요해. 구현 복잡도는 높아도 사용자에게
적합하다면 과감하게 이야기하는것도 필요하고.
여기서 전문가 한명을 더 추가할게 — 각 대화자의 내용을
종합적으로 이해하고 어떻게 종합할지, 필요한 부분은 뭐고
덜어낼건 뭔지를 정리하는 역할이야. 역시 UX 전문가이지.
```

**페르소나 구성:**

```
참가자:
- 수진 — 사용자 심리/행동 전문가
- 현우 — 디자인/모션/시각 효과 전문가
- 민재 — 서비스 철학 전문가 (미니멀 소프트웨어)
- 지은 — UX 종합 설계자 (통합/정리 역할) ← 사용자가 추가
```

**토론 흐름 패턴:**

```
[지은 (종합)] 시작 전 맥락 정리:
"현재 상황을 정리합니다. 방안 A를 시도했고,
사용자 피드백 두 가지를 받았습니다:
1. 플로팅 박스가 직관적이었는데 헤더로 가니 뭔지 몰랐다
2. 상단 작업공간 탭 자체도 깔끔하지 않다
이 맥락에서 각자 의견을 주세요."

[수진 (심리)] 이론 기반 분석 + 사용자 행동 패턴 제시:
"인지심리학에서 '팝아웃 효과'라고 합니다. 분리된 물체는
즉시 '이건 별도의 것'으로 인식됩니다.
사용자의 시선 흐름을 생각하면:
1. 대화 읽을 때: 중앙 위→아래
2. 메시지 쓸 때: 하단 입력 고정
3. 패널 열고 싶을 때: '대화→탐색' 모드 전환 순간
세 번째가 핵심이에요. 의도적 전환이니 살짝 의도를 가지고
접근해야 하는 위치에 있어도 괜찮습니다."

[현우 (디자인)] 수진 의견에 반응 + 구체적 시각 아이디어 3개:
"수진이 말한 '의도적 전환'에 동의합니다. 그 관점에서:
아이디어 1: 채팅 영역 좌측 가장자리 세로 배치 — 문 손잡이 메타포
아이디어 2: 엣지 피크 — 평소 아이콘 절반만, hover 시 전체 나타남
아이디어 3: 스크롤 최상단 트리거 — 맨 위로 올리면 토글 나타남"

[민재 (철학)] 현우 아이디어에 반박 + 대안 제시:
"현우 아이디어 중 짚을 게 있어요. 아이디어 1 — 좋은데,
좌측은 이미 트리 사이드바가 열리는 영역이에요.
겹치니까 복잡해집니다. 대신 제가 생각하는 건:
아이디어 4: 헤더 최소화. 작업공간 탭을 드롭다운으로 숨기면
헤더가 얇아지면서 토글바 위치 선택지가 넓어져요."

[수진] 민재 아이디어에 근거 추가:
"민재의 아이디어 4가 맞아요. 작업공간 전환은 세션 단위(1시간 1-2번).
토글은 수시. 빈도에 비해 시각적 비중이 과도합니다.
'고빈도 = 쉬운 접근, 저빈도 = 숨겨도 됨' 원칙으로 보면..."

[현우] 수진 변형을 발전시킴:
"수진의 변형이 좋은데, 디자인적으로 문제가 있어요.
입력 위에 그냥 넣으면 하단에 두 줄이 쌓여 무거워져요.
아이디어 5: 입력 wrapper 안에 통합하되 상단 영역으로 분리.
하나의 카드 안에 토글+입력. '액션 허브'로 인식."

[민재] 현우 아이디어 지지 + 주의점:
"'액션 허브' — 서비스 철학과 맞아요. '생각의 도구들을 한 곳에'.
다만 토글 영역은 비활성 시 매우 낮은 시각적 강도여야 합니다.
'있지만 조용한(present but quiet)' 상태가 핵심이에요."

[지은 (종합)] 중간 정리:
"여기까지 정리합니다.

나온 핵심 원칙들:
┌──────────────┬──────┬──────────────────────────────────┐
│     원칙     │ 출처 │              설명                │
├──────────────┼──────┼──────────────────────────────────┤
│ 팝아웃 효과  │ 수진 │ 주변과 시각적 분리 = '추가 기능' │
│ 모드 전환    │ 수진 │ 패널 열기는 의도적 전환           │
│ 빈도 = 비중  │ 수진 │ 고빈도 = 쉬운 접근               │
│ 물리적 메타포│ 현우 │ 문 손잡이처럼 열릴 방향에 배치    │
│ 조용한 존재감│ 민재 │ present but quiet                 │
└──────────────┴──────┴──────────────────────────────────┘

합칠 것: 아이디어 4 + 5 → 헤더 얇아지면서 하단 액션 허브가 유일한 도구 영역
덜어낼 것: 아이디어 3(스크롤 트리거) → 발견성 너무 낮음
미결: 아이디어 5의 구체적 레이아웃, 엣지 피크와 조합 여부"

[지은] "각자 한 마디 — '이건 꼭' 또는 '이건 절대 안 됨' 있으면?"

[수진] "아이디어 5는 꼭. 입력 포커스 시 토글 fade out 하면 인지 부하도 해결."
[현우] "엣지 피크 완전히 버리긴 아까워요. 모바일에서는 이게 공간 아낌."
[민재] "헤더 최소화는 분리해서 별도로. 커플링되면 양쪽 다 중도반단."

[지은] 최종 정리:
"1순위: 아이디어 5 (입력 wrapper 통합)
2순위: 헤더 최소화 (별도 이터레이션)
보류: 엣지 피크 (모바일 반응형에서 재검토)"
```

**이 예시에서 관찰되는 패턴:**
- 종합 역할(지은)이 시작/중간/마무리에서 구조화
- 각 페르소나가 앞 발언자를 인용하며 동의/반박/발전
- 전문 영역의 이론과 근거를 구체적으로 제시 (팝아웃 효과, 어포던스 등)
- "좋은데 문제가 있어요" 형태의 건설적 반박
- 종합 정리가 표+합칠것/덜어낼것+미결 형식
- 마무리에 각자 한 마디로 방향 수렴

```bash

출력:
  토론 진행 중 (라운드 1)
  종합: 지은 — 맥락 정리 완료

  [발언 완료] 현우 (비주얼 디자이너)

discuss summarize

# 토론 종료 — 종합 역할이 최종 정리
discuss end
```

```python
class Facilitator:
    """메인 퍼실리테이터 - 메인 프로세스"""

    def __init__(self, ai_client: AIClient):
        self.ai_client = ai_client
        self.context = []  # 메인 컨텍스트 (사용자와의 대화)
        self.personas: Dict[str, PersonaProcess] = {}
        self.consultation_doc = None
        self.opinion_doc = None

    def consult(self, user_message: str) -> str:
        """상담 단계 - 사용자와 1:1 대화"""
        self.context.append({"role": "user", "content": user_message})
        response = self.ai_client.chat(self.context)
        self.context.append({"role": "assistant", "content": response})
        return response

    def propose_personas(self) -> List[PersonaProfile]:
        """상담 결과 기반 페르소나 제안"""
        pass

    def create_persona(self, profile: PersonaProfile) -> PersonaProcess:
        """서브 프로세스 생성"""
        process = PersonaProcess(
            profile=profile,
            ai_client=self.ai_client,
            shared_context=self.consultation_doc
        )
        self.personas[profile.name] = process
        return process

    def invoke_persona(self, name: str, query: InvokeQuery) -> PersonaResponse:
        """서브 프로세스 호출"""
        persona = self.personas[name]
        response = persona.respond(query)
        # 결과를 메인 컨텍스트에 추가
        self.context.append({
            "role": "assistant",
            "content": f"[{name}] {response.opinion}"
        })
        return response
```

```python
# core/persona_process.py (신규)

class PersonaProcess:
    """서브 프로세스 - 독립 컨텍스트를 가진 페르소나"""

    def __init__(self, profile: PersonaProfile, ai_client: AIClient, shared_context: str):
        self.profile = profile
        self.ai_client = ai_client
        self.history = []  # 이 페르소나만의 독립 히스토리
        self.system_prompt = profile.system_prompt

        # 초기 컨텍스트: 상담 문서 요약
        self.history.append({
            "role": "system",
            "content": f"{self.system_prompt}\n\n[상담 요약]\n{shared_context}"
        })

    def respond(self, query: InvokeQuery) -> PersonaResponse:
        """쿼리에 응답 (히스토리에 누적)"""
        self.history.append({
            "role": "user",
            "content": query.to_prompt()
        })
        response = self.ai_client.chat(self.history)
        self.history.append({
            "role": "assistant",
            "content": response
        })
        return PersonaResponse(
            persona=self.profile.name,
            opinion=response
        )
```

```python
import asyncio

async def invoke_all_personas_parallel(
    facilitator: Facilitator,
    query: InvokeQuery
) -> Dict[str, PersonaResponse]:
    """모든 페르소나를 병렬로 호출 (1라운드용)"""
    tasks = {}
    for name, process in facilitator.personas.items():
        tasks[name] = asyncio.create_task(process.respond_async(query))

    responses = {}
    for name, task in tasks.items():
        responses[name] = await task
    return responses
```

```python
def compress_history(history: List[Dict], max_tokens: int) -> List[Dict]:
    """서브 프로세스 히스토리가 너무 길어지면 오래된 부분 요약"""
    if estimate_tokens(history) > max_tokens:
        old = history[1:-4]  # system prompt와 최근 4개 제외
        summary = summarize(old)
        return [history[0], {"role": "system", "content": f"[이전 대화 요약] {summary}"}] + history[-4:]
    return history
```
